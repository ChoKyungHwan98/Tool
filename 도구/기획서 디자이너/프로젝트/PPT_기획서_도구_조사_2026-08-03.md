# PPT 기획서 작성 도구 조사 보고서

- 조사 기준일: 2026-08-03
- 목적: 사용자가 제공한 `슬라이드 빌드 지침 v3`를 실제 프로그램으로 구현할 때 재사용할 수 있는 오픈소스·상용 도구를 찾고, 그대로 사용·개조·조합 중 무엇이 합리적인지 결정한다.
- 핵심 결론: 현재 공개된 단일 프로젝트 중 v3의 콘텐츠 게이트, 근거 추적, 네이티브 PPTX, Pretendard 임베드, 이미지 슬롯 및 빌드 후 보고까지 모두 충족하는 것은 없었다. 장기적으로는 [Oh My PPT](https://github.com/arcsin1/oh-my-ppt)를 앱 기반으로 삼고, `Gate Engine`과 엄격한 네이티브 출력 경로를 추가하는 방식이 가장 가깝다. 빠른 검증용으로는 [PPT Master](https://github.com/hugohe3/ppt-master)를 v3 전용 스킬로 개조하는 편이 낫다.

## 1. 조사 범위와 방법

### GitHub

GitHub 공개 검색 API에서 아래 계열의 검색어를 사용했다.

- `pptx generator`
- `powerpoint generator`
- `presentation generator AI`
- `slide generator AI`
- `text to pptx`
- `markdown pptx`
- `html pptx`
- `topic:pptx`
- `topic:presentation-generator`

1차 결과 852건에서 중복을 제거해 663개 저장소를 후보 풀로 만들었다. 이후 AI 프레젠테이션, 에이전트, editable PPTX, Office 자동화 검색을 추가해 후보를 보완했다. 스타는 발견 우선순위로만 사용하고, 최종 판정은 실제 README, 소스, 라이선스, 출력 샘플로 했다.

### Gitee

Gitee 공개 검색 API는 같은 날짜에 `ppt` 검색도 0건을 반환해 신뢰할 수 없었다. 따라서 [Gitee 검색 화면](https://so.gitee.com/?q=ppt)에서 스타순 결과를 직접 확인하고, 관련 저장소는 개별 저장소 API와 페이지를 교차 확인했다.

### 기타

- npm 패키지 레지스트리에서 PPTX 변환 핵심 모듈의 버전과 라이선스를 확인했다.
- 상용 제품은 각 제품의 공식 기능·도움말 문서를 기준으로 비교했다.
- 상위 오픈소스는 소개 문구만 보지 않고 샘플 PPTX의 ZIP 구조와 실제 구현 소스를 확인했다.

### 이 보고서에서 말하는 “전체 조사”의 범위

공개 검색으로 접근 가능한 저장소와 공식 제품 문서를 폭넓게 훑은 결과다. 비공개 저장소, 검색 엔진에 노출되지 않는 프로젝트, API 결과 상한 밖의 저신호 저장소까지 문자 그대로 모두 수집했다는 뜻은 아니다. 대신 관련 검색어를 교차 사용하고, 고스타·고적합 후보는 소스와 산출물까지 검증했다.

| 조판 | 주장에 맞는 레이아웃 선택, 반복 감지, 히어로 슬라이드 | 카드 그리드와 기본 블루에 고착 |

| 라이선스 | 개인·사내 도구로 개조 가능한 라이선스 | 핵심 내보내기 모듈이 비공개·상용 전용 |

## 3. 결론부터 본 후보 순위

서로 역할이 다른 프로젝트를 하나의 점수로 섞으면 판단이 흐려진다. 따라서 “어디에 쓸 수 있는가”를 기준으로 순위를 나눴다.

| 순위 | 후보 | 가장 적합한 역할 | 판정 |
|---:|---|---|---|

## 4. 핵심 후보 심층 검증

### 4.1 Oh My PPT — 장기 앱 기반 1순위

[Oh My PPT](https://github.com/arcsin1/oh-my-ppt)는 Electron 기반 로컬 우선 앱이다. 주제 또는 문서에서 아웃라인과 덱을 만들고, 채팅과 직접 조작으로 수정하고, editable PPTX로 내보내는 흐름을 이미 갖고 있다. 2026-08-03 스냅샷 기준 1,825 stars, Apache-2.0이었다.

확인된 강점:

- 문서 업로드, 주제 입력, 대화형 요구 정리, 아웃라인, 스타일, 시각 편집, 버전 기록이 한 앱에 있다.
- 사용된 글꼴을 추출하고 WOFF2를 PowerPoint 임베드 형식으로 변환하는 코드가 있다.
- `PPTX font embedding` 단위 테스트와 `collectEmbeddedFonts` 구현이 실제 소스에 존재한다.
- 핵심 패키지 `@arcsin1/html2pptx`, `@arcsin1/pptx2json`, `@arcsin1/pptx-ooxml-geometry`도 npm 메타데이터상 Apache-2.0이다.
- 단순 HTML 표는 editable DrawingML 표로 내보내고, 복잡한 표는 편집 가능한 도형·텍스트로 풀어내는 경로가 있다.

확인된 한계:

- 삽입 차트는 Chart.js `canvas`로 구현돼 있다. exporter 문서상 `canvas`는 PowerPoint 이미지로 변환되므로 v3의 네이티브 차트 조건을 통과하지 못한다.
- SVG 역시 현재 exporter에서는 래스터 이미지가 된다. 상태도·판정 타임라인은 HTML SVG가 아니라 PowerPoint 도형·선으로 생성해야 한다.
- 복잡한 차트·표·도형·애니메이션은 프로젝트 문서도 “개선 중”이라고 밝힌다.
- 생성 전에 자료를 정리하는 기능은 있지만, Gate A/B/C를 각각 승인하고 잠그는 상태 머신은 없다.
- 슬라이드 문장과 원문 ID를 연결하는 provenance ledger, `[DATA REQUIRED]`, 이미지 슬롯 보고, 빌드 후 콘텐츠 매핑이 없다.

판정: **사용자용 제품의 껍데기로 가장 좋다.** 빈 앱부터 만드는 비용을 피하면서 사용자에게 필요한 목차 조정, 대화, 시각 편집 경험을 확보할 수 있다. 다만 exporter를 그대로 “v3 준수”라고 부를 수는 없다.

### 4.2 PPT Master — 빠른 v3 프로토타입 1순위

[PPT Master](https://github.com/hugohe3/ppt-master)는 에이전트가 주장과 디자인 명세를 먼저 만들고 SVG를 거쳐 PowerPoint DrawingML로 변환하는 생성 도구다. 2026-08-03 스냅샷 기준 42,643 stars, MIT였다.

확인된 강점:

- 슬라이드 제작 전에 argument와 design specification을 다루는 구조가 v3의 Gate B/C와 가깝다.
- 텍스트, 도형, 커넥터, 다이어그램이 네이티브 DrawingML로 나간다.
- 선택 옵션으로 실제 PowerPoint 차트·표 객체를 만들 수 있다.
- 디자인 명세 잠금, QA, overflow 검사, 전달 전 검사가 이미 있다.
- Claude·Codex류 에이전트 스킬로 붙이기 쉽다.

실제 샘플 검증:

- 공식 예제 `swiss_grid_systems.pptx`를 내려받아 ZIP 구조를 검사했다.
- 14 slides, 1 master, 11 layouts였고 전 장에 라이브 텍스트와 도형이 있었다.
- 네이티브 표·차트 객체는 없었고, 그림이 포함된 슬라이드는 3장이었다.
- `ppt/fonts/`와 `embeddedFontLst`가 없어 글꼴은 임베드되지 않았다.

한계:

- 기본 구조에는 Gate A의 원문 인벤토리와 주장·수치 출처 역추적이 없다.
- Gate C와 유사한 설계 단계는 있으나 사용자가 준 정확한 스토리보드 표 승인 계약은 아니다.
- 폰트 임베드 구현이 확인되지 않았다.
- 완성형 데스크톱 편집 앱이 아니다.

판정: **가장 빠르게 사용자의 지침을 작동시키는 프로토타입을 만들기 좋다.** Gate A/B/C JSON 스키마와 승인 잠금, Oh My PPT의 글꼴 임베드 방식을 붙이면 짧은 경로가 된다.

### 4.3 OfficeCLI — 최종 파일 검증과 네이티브 조작

[OfficeCLI](https://github.com/iOfficeAI/OfficeCLI)는 PowerPoint·Word·Excel 파일을 읽고 만들고 수정하는 CLI다. 2026-08-03 스냅샷 기준 24,462 stars, Apache-2.0이었다.

적합한 용도:

- 기존 PPTX의 텍스트, 폰트, 색, 레이아웃, 수식, 차트, 이미지 수정
- 렌더링과 검증을 반복하는 자동 QA
- 템플릿과 placeholder 병합
- 생성 후 네이티브 차트 삽입 또는 잘못된 객체 교정

부적합한 용도:

- 스스로 목차와 논리를 설계하는 제품이 아니다.
- Gate A/B/C 사용자 경험은 별도로 만들어야 한다.

판정: **앱이 아니라 후처리·검증 엔진으로 쓴다.**

### 4.4 Presenton — 설치해서 비교할 오프더셸프 기준점

[Presenton](https://github.com/presenton/presenton)은 프롬프트와 문서에서 프레젠테이션을 만들고 editable PPTX/PDF로 내보내며, 자체 호스팅·데스크톱·MCP를 지원한다. 공식 문서는 [Presenton Docs](https://docs.presenton.ai/index)에서 확인할 수 있다. 2026-08-03 기준 9,287 stars, Apache-2.0이었다.

장점은 앱 완성도와 설치 편의다. 단점은 사용자의 v3가 강조하는 “슬라이드를 만들기 전에 승인받고, 모든 주장과 수치를 원문 ID에 묶는 것”이 제품의 핵심 계약이 아니라는 점이다.

판정: **개발 전에 실제로 설치해 결과 품질과 작업 시간을 비교할 기준점**으로 가치가 있다. 그대로 최종 도구로 채택할 가능성은 낮다.

### 4.5 PPTAgent — 생성 알고리즘 참고

[PPTAgent](https://github.com/icip-cas/PPTAgent)는 레퍼런스 프레젠테이션에서 슬라이드 기능 유형과 콘텐츠 스키마를 분석하고, 아웃라인을 만든 뒤 편집 동작을 반복하는 연구형 에이전트다. 2026-08-03 기준 4,882 stars, MIT였다.

사용자가 원하는 “논리를 시각 구조로 번역한다”는 문제에 가깝지만, 승인 UI와 실무용 편집 경험을 갖춘 완성 앱은 아니다. 레퍼런스 덱을 활용하는 알고리즘만 가져오는 편이 낫다.

## 8. 권고 아키텍처

### 장기안: Oh My PPT 포크 + Gate Engine + Strict PPTX Export

```text
자료 입력
  ↓
Gate A: 콘텐츠 인벤토리 / 주장·수치 source_id / 누락 데이터
  ↓ 사용자 승인 및 잠금
Gate B: 디자인 브리프 2~3안 / 모티프 / 히어로 / 내비게이션
  ↓ 사용자 선택 및 잠금
Gate C: 슬라이드 주장 / 구조 유형 / 시각 형식 / 근거 ID
  ↓ 사용자 승인 및 잠금
Deck Spec JSON
  ↓
HTML 편집 캔버스 + 네이티브 객체 명세
  ↓
PPTX 생성 → 폰트 임베드 → 네이티브 차트·표 보강 → 렌더·구조 QA
  ↓
PPTX + DATA REQUIRED + 이미지 슬롯 + 콘텐츠 매핑 + 변경 보고
```

핵심 데이터 모델:

- `source_items`: 원문, 유형, 파일·페이지·문단 위치, 해시
- `claims`: 슬라이드에 쓸 문장, 연결된 `source_item_id[]`, 사용자 승인 상태
- `data_gaps`: `[DATA REQUIRED]` 필드, 필요한 단위와 목적
- `design_briefs`: 팔레트, 모티프, 히어로 후보, 흐름 내비게이션
- `slide_specs`: 헤드라인, 구조 유형, 시각 형식, 근거 ID, 이미지 슬롯
- `approvals`: Gate별 버전, 승인 시각, 승인 후 변경 이력
- `qa_findings`: 반복 구성, 악센트 비율, 미매핑 문장, 폰트·객체 검사
- `export_runs`: 사용한 spec 버전, PPTX 해시, 보고서

반드시 코드로 강제할 규칙:

1. 승인되지 않은 Gate가 있으면 `Build` 버튼을 비활성화한다.
2. 수치와 고유명사는 `source_item_id` 없이는 Deck Spec에 저장하지 못하게 한다.
3. 숫자 누락은 LLM이 채우지 않고 `[DATA REQUIRED]`로만 만든다.
4. 시스템·메커니즘 슬라이드는 수치 표, 상태도·판정 타임라인, 엣지 케이스, 검증 계획 중 하나가 없으면 실패 처리한다.
5. 같은 시각 형식 3연속, 같은 바디 구성 3연속을 validator가 검출한다.
6. 이미지 슬롯은 배경 패널과 주석 레이어를 서로 다른 객체로 생성한다.
7. 최종 PPTX ZIP에서 `ppt/fonts/*`, `embeddedFontLst`, 슬라이드 크기, live text, chart/table 객체를 검사한다.
8. 렌더 이미지 비교와 텍스트 overflow 검사를 통과해야 내보내기를 완료한다.

### 네이티브 출력 전략

- 텍스트·도형·단순 표·폰트: Oh My PPT의 Apache-2.0 exporter를 사용한다.
- 상태도·타임라인·도판: SVG를 넣지 말고 PowerPoint 도형·선·커넥터 명세로 생성한다.
- 차트: Chart.js canvas 경로를 금지하고 데이터와 차트 유형을 별도 JSON으로 유지한다. 최종 PPTX에는 [PPT Master](https://github.com/hugohe3/ppt-master), [OfficeCLI](https://github.com/iOfficeAI/OfficeCLI), 또는 직접 확장한 OOXML writer로 네이티브 차트를 삽입한다.
- Pretendard: 프로젝트 font asset으로 고정하고 사용한 웨이트만 subset 임베드한다. 파일의 embedding 권한 비트도 사전 검사한다.

## 9. 빠른 프로토타입과 장기 제품을 나누는 것이 좋은 이유

### 빠른 프로토타입

PPT Master에 사용자의 v3를 스킬 규칙과 JSON 스키마로 붙인다.

- 장점: Gate A/B/C와 보고 형식이 실제 작업 시간을 줄이는지 먼저 검증할 수 있다.
- 추가 작업: 승인 상태 저장, source ID validator, `[DATA REQUIRED]`, 이미지 슬롯, 폰트 임베드 후처리.
- 사용 경험: Codex·Claude류 대화 안에서 승인하고 `.pptx`를 받는다.

### 장기 제품

검증된 워크플로를 Oh My PPT UI로 옮긴다.

- 장점: 목차 편집, 아웃라인 드래그, 슬라이드 편집, 버전 기록, 내보내기가 하나의 앱에 들어간다.
- 추가 작업: Gate 화면 3개, provenance 패널, 상세 밀도 검사기, Strict Export, QA 보고 화면.

이 순서라면 UI를 오래 만든 뒤 워크플로 자체가 불편하다는 사실을 발견하는 위험을 줄일 수 있다.

## 10. 권고하지 않는 선택

- 처음부터 PPT 편집기와 exporter를 모두 새로 만드는 것
- Canva·Gamma류 산출물을 이미지 PPTX로 받아 후처리하는 것
- Marp·HTML 스크린샷을 editable PPTX라고 간주하는 것
- LLM 프롬프트만으로 “근거 없는 수치 생성 금지”를 보장하는 것
- 스타 수만 보고 2026년 신생 프로젝트를 검증 없이 기반으로 채택하는 것

## 11. 다음 단계 제안

1. `PPT Master + v3 Gate JSON + Pretendard 임베드`로 5~8장짜리 실제 게임 기획서 한 건을 만든다.
2. 같은 원문을 Presenton과 Oh My PPT에도 넣어 소요 시간, 논리 품질, 레이아웃 수정량, PPTX 객체 편집성을 비교한다.
3. 프로토타입에서 Gate A/B/C가 실제로 시간을 줄이면 Oh My PPT 포크를 시작한다.
4. 첫 앱 버전의 범위는 “원문 인벤토리 → 스토리보드 승인 → 16:9 PPTX → 필수 보고서”까지만 잡는다. 고급 애니메이션과 자유형 디자인은 뒤로 미룬다.
